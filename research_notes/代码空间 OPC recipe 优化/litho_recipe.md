# LLM-driven optimization of computational-lithography recipes (OPC / ILT / SMO / SRAF), up to Nov 2026

Verification levels: **V-code** = I read the released code/data myself; **V-snippet** = only search-engine snippets / abstract summaries; **V-3rd** = third-party summary site (Liner, Moonlight, EmergentMind); **U** = unverified / could not find.
Network note: arxiv.org, alphaxiv, semanticscholar, cse.cuhk.edu.hk and true-litianyi.github.io were blocked in this session (proxy 403 / DNS). GitHub raw (raw.githubusercontent.com) worked. So paper PDFs were not read; repo code and data were.

## Q1. Which works optimize OPC/ILT/SMO recipes with LLMs in code/config space? Representation, search algorithm, evaluator, budget, results

### Takeaway
Only a few works truly have an LLM edit a lithography *recipe* as text and use a simulator in the loop. The clearest is **VPEvolve** (arXiv 2609.32473, ~Sep 2026). It edits whitelisted lines of a Calibre SVRF/LITHO deck (MBSRAF + DenseOPC options) under typed operations, with commercial Calibre as the evaluator and a budget of 10 candidates per case. The **Intelligent OPC Engineer Assistant** (AAAI 2025) uses RL (PPO) to search recipe parameters and an LLM only to distil the results into a rule/tree recipe. **MASK/Agent Lab** (NanWang-EE, 2026) is an LLM-in-the-loop *mask* optimizer on OpenILT: it edits geometry segments directly, not an ILT recipe. I found no LLM work that optimizes SMO settings or ILT loss/regularizer/schedule configs as code.

### Cited Findings

**A. VPEvolve: "A Self-Evolving Virtual Process Engineer for Computational Lithography" (arXiv 2609.32473; Tianyi Li + 7 co-authors; ~Sep 2026; experiment seed in config `2026092001`)**
- Paper identity, authors and the frozen-LLM + "Skill Bank" design (the Skill Bank turns trial feedback into scoped, evidence-linked judgments via LLM reflection/curation; weights are not updated). V-snippet. — [arXiv abs](https://arxiv.org/abs/2609.32473); [arXiv HTML](https://arxiv.org/html/2609.32473)
- Headline results (V-snippet; the paper text was not readable here): on a FreePDK45-derived benchmark with ten commercial-tool evaluations per case, mean per-case **max EPE goes from 18.294 → 5.361 nm on Poly and 22.052 → 15.692 nm on Metal1** (≈71% and ≈29%). The snippet says final mean EPE is "nearly unchanged on Poly and lower on Metal1 (0.693 vs 0.698 nm)", which is garbled; treat it with care. — [arXiv HTML](https://arxiv.org/html/2609.32473)
- Agent baselines (V-snippet): ReAct is the strongest agent baseline on max EPE (16.501 / 17.775 nm). VPEvolve improves on it by 67.5% (Poly) and 11.7% (Metal1). Among backbone LLMs, Gemma and DeepSeek reach the lowest max EPE and GLM and Claude lead on mean EPE. — [arXiv abs](https://arxiv.org/abs/2609.32473); [arXiv HTML](https://arxiv.org/html/2609.32473)
- Repos: `vpevolve/vpevolve_code_and_data` and `True-Litianyi/VPEVOLVE_code` have **identical READMEs** (Apache-2.0). Both contain the agent code, a standalone differentiable litho simulator (`diff_litho`, TCC modes at focus −30/0/+30 nm, 193 nm analytic config) and 20 FreePDK45-derived GDS windows (10 Poly, 10 Metal1). Download: `downloads/vpevolve-full-source-0.4.0.zip`. V-code. — [README](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/README.md); [mirror README](https://raw.githubusercontent.com/True-Litianyi/VPEVOLVE_code/main/README.md)
- **Evaluator**: the experiment pipeline requires a licensed **Siemens Calibre** install (`calibre`, `pdl_lib_mgr`) plus a user-supplied optical/resist model. "No substitute model or simulated evaluation is used when these dependencies are missing." The bundled simulator "is not a replacement for the commercial OPC recipe correction and evaluation pipeline." V-code. — [README](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/README.md)
- **Recipe representation (V-code, from the release zip)**: each case has an initial recipe `data/assets/cases/<case>/R0.svrf` plus `layout.gds`. R0 is a full Calibre SVRF deck: "Auto-generated Metal MBSRAF + DenseOPC + OPCVerify deck". It contains `RET MBSRAF` with a `LITHO FILE MBSRAF_SETUP` (`sraf_options`: minwidth 0.03, maxwidth 0.035, minoffset 0.05, maxoffset 0.3, …), `LITHO DENSEOPC` with `denseopc_options METAL_OPTS` (jog_freeze 0.010, max_opc_move 0.05, max_iter_movement 0.005, fragment_min 0.025, fragment_max 0.060, fragment_corner rules, `feedback -0.3 -0.4 -0.5 -0.6 -0.7 -0.6 -0.5 -0.4 -0.3 -0.2`, a sequence of `OPC_ITERATION` statements, sraf print avoidance) and `LITHO OPCVERIFY` outputs (EPE, PV band, …). — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- **What the LLM may edit (V-code, `environment/kernels/recipe_validation.py`)**: only recognized lines inside the two option blocks `denseopc_options METAL_OPTS` and `sraf_options METAL_SRAF_OPTS`. Everything else is a "protected physical contract", and a child is rejected if the protected projection changes or if there is "No physical change". The editable families are numeric params with hard bounds: jog_freeze [0, 0.05], jog_ignore_metric, max_opc_move [0.001, 0.10], max_iter_movement [0.0001, 0.03], fragment_min, fragment_grid, fragment_minjog, and the SRAF minwidth/maxwidth/maxlength/extension/minlength/minsquarelength/minoffset/maxoffset/minfeaturespace. Enums: line_end_fragment on/off. Free-form-line families: `fragment_max`, `fragment_corner`, `feedback` (schedule), `OPC_ITERATION`, `sraf_sites_create`, `sraf_print_avoidance`. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- **Action schema (V-code, `evolution/actions.py`, `kernels/operations.py`)**: a proposal is JSON carrying `parent_sha256`. It must include the reasoning fields `diagnosis`, `expected` and `falsification` (hypothesis-style experiment design). It then gives `operations` (each one is `replace` / `delete` / `insert_after` on a catalogued editable line id, with new command lines and no braces) and/or `local_rules` (≤6 local displacement rules with fields asset_ref, edge_bbox_um, focus_um, normal, reach_um, delta_nm). Local rules are applied "after final OPC and before verification" on one source-edge occurrence, which makes them a hotspot-fix action. Agent tools: inspect_state, query_trials, read_evidence, read_judgment, build_pattern, compile_candidate, run_trial, query_experience, update_experience. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- **Search / selection (V-code, `environment/objective.py`)**: single-trajectory accept/reject (hill-climb), not a population. A child is retained only if it is feasible and lexicographically better on (max EPE, top-10 mean EPE, mean EPE, PV-band area per target edge). Hard constraints: MRC result count = 0 and SRAF printability violations = 0. Mean EPE and PVB may not exceed 1.02× R0 (`quality_ratio 1.02`). Config `evolution_strategy: "search_guided"` uses a measured "search board" of feasible trade-offs; `decision_policy: "advisory"`. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- **Budget (V-code, `configs/experiments/poly_01/full.json`)**: `candidates: 10, model_calls: 180, opc_calls: 12, pattern_jobs: 10`, described as "10 optimization rounds from R0" with an empty initial experience store. The 12 OPC calls likely cover R0 and a terminal repeat (`terminal_repeat: true`) on top of the 10 candidates; that reading is my inference. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- **LLM & framework (V-code)**: the default `configs/model.json` is `Qwen/Qwen3.6-27B` served locally via vLLM (OpenAI-compatible endpoint), temperature 0, thinking off, 131k context. It has three roles (actor / reflector / curator), with reflector and curator prompts adapted from **ACE (Agentic Context Engineering)**. The orchestration harness is **Pi** (`@earendil-works/pi-coding-agent` 0.85.1, a TypeScript host). **No LangGraph** (grep for "langgraph" over the release found nothing). Ablations: `frozen` (no online experience), `without_m1` (domain reflection), `without_m2` (condition-aware revision), `without_m3` (prospective advice). Baseline methods registered in code: raw, static, react, textual, reasoningbank, ace, vpevolve. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- Engineering-prior "skills" shipped as markdown (`evolution/skills/engineering.md`, `search.md`). Example: "Inspect fragmentation (fragment_min/max and jog_freeze), movement limits and the feedback schedule together…"; "Do not split a supported bundle solely to identify its cause during a four-trial optimization." V-code. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- Note: the README says "Empty-start runs are a different protocol from earlier source-seeded results". So the repo's protocol may differ from the numbers in the paper. V-code. — [README](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/README.md)

**B. Intelligent OPC Engineer Assistant for Semiconductor Manufacturing (Guojin Chen, Haoyu Yang, Bei Yu, Haoxing Ren; CUHK + NVIDIA; arXiv 2408.12775, Aug 2024; AAAI 2025, vol. 39 no. 22, DOI 10.1609/aaai.v39i22.34479)**
- Two stages: (1) RL searches the OPC recipe, (2) a multi-modal LLM agent summarizes the RL results and generates the final rule-based OPC recipe, which "maintains the same runtime as the pure OPC engine". V-snippet. — [arXiv](https://arxiv.org/abs/2408.12775); [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/34479)
- The RL stage uses PPO to decide how to place/adjust **EPE measurement points and fragmentation points**, with a loss combining distance, EPE and PVB terms. The LLM labels features from the RL outputs, and a decision/regression tree built on those labels yields the recipe (author's Notion: "Agent System with LLM-labeled Regression Tree"). V-3rd. — [EmergentMind API](https://api.emergentmind.com/papers/2408.12775); [author Notion](https://gjchen.notion.site/Agent-System-with-LLM-labeled-Regression-Tree-44ae87a389524ba3b32682af5b45a54d); [Moonlight](https://www.themoonlight.io/review/intelligent-opc-engineer-assistant-for-semiconductor-manufacturing)
- Results (V-3rd; summaries conflict). ICCAD13: the LLM recipe gives ≈11% fewer EPE violations and ≈19% lower EPE distance; one summary instead gives RL at 12% / ~24%. NVDLA: RL gives 13% / 15% and the LLM recipe 8% / 12%. — [EmergentMind](https://www.emergentmind.com/papers/2408.12775); [Liner](https://liner.com/review/intelligent-opc-engineer-assistant-for-semiconductor-manufacturing)
- The paper is on Bei Yu's site as `C251-AAAI2025-OPCAgent.pdf`, which was not readable here. — [CUHK PDF](https://www.cse.cuhk.edu.hk/~byu/papers/C251-AAAI2025-OPCAgent.pdf)

**D. Adjacent LLM work: SRAF / SVRF generation (not recipe search)**
- **LLM-SRAF** (DATE 2025, CUHK): a fine-tuned LLM generates SRAFs, and its output is checked with Calibre lithography simulation. This is a generation model, not a recipe-search loop. V-snippet (a later search failed to re-find it). — [PDF](https://www.cse.cuhk.edu.hk/~byu/papers/C256-DATE2025-LLM-SRAF.pdf)
- **AST-guided LLM for SVRF code synthesis** (arXiv 2507.00352, ICLAD 2025): fine-tuned T5 models on serialized SVRF ASTs. It reports that general LLMs hallucinate heavily on SVRF and that public data is scarce. Its scope names DRC/LVS/OPC and it envisions agentic workflows. It is a one-shot code generator with no optimization loop. V-snippet. — [arXiv](https://arxiv.org/pdf/2507.00352)
- **Rule2DRC** (arXiv 2605.15669, 2026): a benchmark for LLM agents that synthesize DRC scripts, with execution-guided tests. It covers DRC, not OPC. V-snippet. — [arXiv](https://arxiv.org/pdf/2605.15669)

### Inferences
- VPEvolve is the only verified case of "LLM edits a real OPC recipe (Calibre SVRF/LITHO deck) under simulator feedback". Its search space is deliberately narrow: a whitelist of parameters with numeric bounds, structural lines protected, and every edit checked by a compiler/validator. In "code semantic space" terms, the LLM is a *proposal operator over a typed DSL patch*, not a free-form code generator.
- Its search budget is extremely small (10 commercial OPC runs per case). The method is designed for sample efficiency, with hypothesis-style proposals and a reflected experience store, rather than for AlphaEvolve-style throughput.
- The Intelligent OPC Engineer Assistant and VPEvolve sit at opposite ends. In the first, RL does the search and the LLM only summarizes/explains (distillation into rules). In VPEvolve, the LLM itself is the search policy and the memory is natural-language "skills".
- MASK/Agent Lab shows frontier LLMs can drive per-segment mask edits to 0 EPE violations on 2 ICCAD13-style cases in 15 rounds. But it optimizes the *artifact* (mask geometry), not a reusable recipe, so it does not transfer to new layouts the way a recipe does.

### Gaps
- No work found that has an LLM optimize **ILT recipe configs** (loss terms/weights, regularizers, step schedules, initialization, MRC cleanup scripts) or **SMO settings** in code space, as of Nov 2026.
- Not verified from the VPEvolve paper body: per-backbone tables, exact baseline settings, wall-clock/token cost, and whether the paper's numbers come from the Qwen3.6-27B config or other backbones. arXiv was blocked.
- Not verified: the AAAI OPC-Agent's exact LLM (e.g. GPT-4V?), engine (the open-source OpenOPC/Calibre?) and RL budget. Its PDF host was blocked.
- The MASK/Agent Lab publication date and any associated paper were not confirmed. Only the static site repo was found.

## Q2. Does any use LangGraph? Any use evolutionary search over recipe code (AlphaEvolve-style)?

### Takeaway
None of the lithography-recipe works I found uses LangGraph. VPEvolve uses the Pi coding-agent harness plus ACE-style reflector/curator. MASK/Agent Lab uses a custom controller, and the AAAI OPC assistant uses PPO plus a multimodal LLM. None runs AlphaEvolve/OpenEvolve-style population-based evolutionary search over recipe code. VPEvolve's "evolve" means experience/skill evolution with single-parent accept/reject.

### Cited Findings
- VPEvolve runtime deps are `@earendil-works/pi-coding-agent` / `pi-agent-core` 0.85.1 (Node 24) and Python numpy/klayout. ACE prompt templates are adapted for reflector/curator. "langgraph" does not appear anywhere in the release. V-code. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip); [README](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/README.md)
- VPEvolve selection is a single retained parent with lexicographic accept/reject (`objective.decide`). There is no population, island or MAP-Elites archive. V-code. — [repo zip](https://raw.githubusercontent.com/vpevolve/vpevolve_code_and_data/main/downloads/vpevolve-full-source-0.4.0.zip)
- MASK/Agent Lab uses a propose → simulate → accept/rollback controller with one trajectory per model. V-code. — [README](https://raw.githubusercontent.com/NanWang-EE/agent-mask-optimization-site/main/README.md)
- Search for LangGraph + OPC/SMO/lithography agents returned only generic LangGraph material. — [LangGraph docs](https://docs.langchain.com/oss/python/langgraph/overview)
- Search for AlphaEvolve / OpenEvolve / CodeEvolve applied to ILT or OPC found none. General frameworks exist ([AlphaEvolve](https://arxiv.org/html/2506.13131v1), [CodeEvolve](https://arxiv.org/pdf/2510.14150)), and recent ILT work is gradient/ML/RL-based, e.g. generative RL for ILT, arXiv 2602.19027, Feb 2026. — [arXiv 2602.19027](https://arxiv.org/pdf/2602.19027)
- A naming collision to avoid: "VPR-Evolve" (arXiv 2607.24998) is a multi-agent (Planner/Coder/Reviewer) LLM algorithm-evolution system for **FPGA place & route**, not lithography. — [arXiv](https://arxiv.org/pdf/2607.24998)

### Inferences
- An "AlphaEvolve over Calibre/OpenILT recipe code, orchestrated by LangGraph" system seems to be an open slot as of Nov 2026. The closest building blocks are VPEvolve's typed SVRF patch DSL and validator (reusable as a mutation operator and sandbox) and OpenILT as a free, differentiable evaluator for ILT-config evolution.
- With commercial Calibre, each evaluation is expensive and licence-bound (VPEvolve uses `max_concurrent_jobs: 1`), which pushes toward low-budget reflective search rather than population evolution. With an open simulator (OpenILT, VPEvolve's `diff_litho`), a population approach becomes affordable.

### Gaps
- No Chinese-language source (OPC 配方 大模型 / 光刻 recipe 智能体) surfaced beyond re-reports of the AAAI paper. Industrial Chinese work (e.g., domestic EDA vendors) was not found.
- I could not exclude unpublished or vendor-internal LangGraph use.

## Q3. Classical (non-LLM) recipe-optimization baselines and how LLM methods compare

### Takeaway
Classical OPC-recipe auto-tuning is mainly metaheuristic. SPIE work includes genetic algorithms (2016), simulated annealing (2010), automated pattern-coverage flows (2017) and RL for model calibration (2025). Vendors use ML for pattern selection and clustering in recipe tuning (Siemens Calibre SONR). I found no peer-reviewed SPIE paper on Bayesian optimization for OPC recipe tuning. No LLM method reports a head-to-head against GA/SA/BO under the same simulator budget. VPEvolve compares only to LLM-agent baselines (ReAct, ACE, ReasoningBank, …), and the AAAI work compares its RL and LLM recipes to the initial recipe.

### Cited Findings
- "OPC recipe optimization using genetic algorithm" (SPIE 9780, 97800J, 2016; Asthana, Wilkinson, Power): GA tuning of OPC recipe parameters that significantly reduced ORC violations. V-snippet. — [SPIE](https://journals.spiedigitallibrary.org/conference-proceedings-of-spie/9780/97800J/OPC-recipe-optimization-using-genetic-algorithm/10.1117/12.2219166.full)
- "Auto-score system to optimize OPC recipe parameters using genetic algorithm" (SPIE 9985, 998525, 2016): a GA whose objective is based on a scoring system tunes recipe parameters over generations and reduces OPC verification violations. V-snippet. — [SPIE](https://spiedigitallibrary.org/conference-proceedings-of-spie/9985/998525/Auto-score-system-to-optimize-OPC-recipe-parameters-using-genetic/10.1117/12.2241178.full)
- "OPC recipe optimization using simulated annealing" (SPIE 7823, 78233N, 2010; Desouky): optimizes many parameters simultaneously and gives insight into recipe stability. V-snippet. — [SPIE](https://astronomicaltelescopes.spiedigitallibrary.org/conference-proceedings-of-spie/7823/78233N/OPC-recipe-optimization-using-simulated-annealing/10.1117/12.864214.full)

### Inferences
- The relevant baseline gap: no LLM recipe paper found compares against GA/SA/BO/CMA-ES on the same parameter whitelist and simulator budget. With only ~10 evaluations, BO is the natural classical competitor, but neither VPEvolve nor the AAAI work reports it (as far as visible). A fair comparison would put BO/TPE over VPEvolve's NUMERIC bounds (16 numeric params plus enums), at 10 evaluations per case.
- Classical methods tune a fixed numeric vector. The LLM methods add structural edits (feedback schedules, OPC_ITERATION sequences, fragment_corner rules, local hotspot rules) and textual reasoning or memory. That is the claimed advantage, but it is not separately quantified against classical methods.
- For ILT, the "classical baselines" in practice are the ILT algorithms themselves (MOSAIC, LevelSet, MultiLevel, GAN-OPC in OpenILT). MASK/Agent Lab's 15-round LLM trajectory reaches EPE counts comparable to or lower than those on cases 1–2, with worse PVB. That comparison is uncontrolled and covers only n=2.
